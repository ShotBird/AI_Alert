# 10. GitHub "급상승" 신호를 어떻게 만들 것인가

Type: grilling
Status: resolved
Blocked by: (없음)

## Question

[01](01-verify-source-feeds.md)에서 확인된 것: **GitHub API에 "최근 스타 증가분" 필드가 없다.**
응답에는 누적 `stargazers_count`와 `pushed_at`뿐이다.
누적으로 랭킹하면 같은 레포가 몇 달 내내 1등이라 **매일 열어볼 이유가 사라진다.**

선택지:

1. **우리가 매일 스냅샷을 떠서 차분한다** — 하루 한 번 상위 N개 레포의 스타 수를 저장하고 어제와 비교.
   정확하지만 며칠 쌓여야 의미가 생긴다(첫날은 빈 섹션). 저장 위치와 추적할 레포 수를 정해야 한다
2. **`created:>날짜`로 신규 레포만 본다** — 증가분 대신 "이번 주에 새로 생긴 것 중 스타 많은 것".
   첫날부터 동작하고 구현이 단순하다. 단 오래된 강자가 갑자기 뜨는 경우를 놓친다
3. **비공식 트렌딩 스크래퍼 API에 의존** — GitHub 트렌딩 페이지를 긁어 API로 파는 서비스들.
   GitHub이 마크업을 바꾸면 조용히 깨진다
4. **1 + 2 혼합** — 초반엔 2번으로 채우고, 스냅샷이 쌓이면 1번으로 전환

정할 것: 어느 방식인가, 몇 개 레포를 추적하는가, 스냅샷을 어디에 저장하는가(리포에 커밋? 별도 파일?),
그리고 [06](06-skill-taxonomy.md)의 부문 분류 결과를 어떻게 캐시할 것인가.

`grilling` + `domain-modeling` 스킬을 호출할 것.

## Answer

> **에이전트가 대신 결정함** (2026-09-20 야간 자율 세션).

### 이 티켓의 전제가 틀렸다

티켓은 "GitHub API에 최근 스타 증가분 필드가 없다"는 전제 위에 세워졌다. **그건 Search API에 한해서만 맞았다.**
GitHub에는 스타 히스토리 전용 엔드포인트가 있다.

```
GET /repos/{owner}/{repo}/stargazers/history?per_page=3
→ [{"week":1789862400,"total":52,"days":[52,0,0,0,0,0,0]},
   {"week":1789257600,"total":1295,"days":[164,200,236,197,186,144,168]}, ...]
```

직접 두 번 호출해 확인했다 (`anthropics/skills`, `facebook/react` 모두 HTTP 200).
**주별 총계와 일별 분해**를 최신순으로 주고, 레포 생성 시점까지 거슬러 올라간다.
레이트리밋 버킷은 `search`(분당 10회)가 아니라 **`core`** 이고, 헤더로 확인했다:
`X-RateLimit-Resource: core`, 무인증 시간당 60회 / **인증 시 5,000회**.

→ **스냅샷을 직접 쌓을 필요가 없어졌다.** 티켓에 적힌 선택지 1·2·3·4가 전부 불필요해졌다.

### 결정

1. **후보 풀**: Search API로 `topic:agent-skills` + `topic:claude-skills` 상위 200~300개 (하루 2~3회 호출)
2. **증가분**: 후보마다 `stargazers/history?per_page=2` 호출 → 지난 7일 증가분을 **그대로 읽는다** (하루 200~300회, core 버킷)
3. **필터**: [06](06-skill-taxonomy.md)이 정한 제외 규칙을 **먼저** 적용 (모음집·무관 제품·설명 없음)
4. **정렬**: 남은 단일 목적 스킬을 **7일 절대 증가분**으로 줄 세워 상위 5개

**비율(%) 대신 절대 증가분을 쓰는 이유**: 비율로 하면 스타 10개짜리가 3개 늘어 30%로 1등을 한다.
거대 레포가 독식할 위험은 3번 필터가 이미 제거한다 — 주당 1,295개씩 늘어나는 `anthropics/skills`는
**모음집이라 애초에 랭킹에서 빠진다.** 필터를 통과한 단일 스킬들은 규모가 비슷해서 절대값 비교가 공정하다.

### 대가

**GitHub 개인 토큰(PAT)이 필요해졌다.** 무인증 core는 시간당 60회뿐이라 300회를 못 채운다.
토큰은 무료이고 public 읽기 권한만 있으면 된다 → 티켓 11에 발급 작업을 넣었다.

### 버린 것과 그 이유

- **누적 스타 상위 목록** — 실측 결과 상위 20개가 9천~17만 스타 구간이라, 하루 수백 개가 늘어도 **순위가 안 바뀐다.** 매일 같은 화면이 뜬다
- **`pushed_at` + 스타를 급상승 대리 신호로** — 실측 결과 누적 상위 목록과 **거의 동일**했다. 큰 레포는 스타와 무관하게 매일 푸시된다. 대리 신호로 실패
- **직접 스냅샷 DB** — 히스토리 엔드포인트가 생성 시점까지의 데이터를 이미 갖고 있어 불필요. 게다가 스냅샷 방식은 **며칠 쌓여야 의미가 생기는데** 이건 첫날부터 진짜 순위가 나온다
- **서드파티(star-history.com 등)** — 2026년 9월 그들의 "새 Star History API" 글은 **GitHub 자체 엔드포인트를 소개한 것**이었다. 중개자가 필요 없다

### 첫날부터 제대로 나온다

스냅샷 방식이었다면 "day 1은 빈 화면, day 30부터 쓸만함"이 됐을 것이다.
히스토리 엔드포인트 덕분에 **1일차 출력이 이미 진짜 주간 랭킹**이고, 비용도 첫날부터 일정하다.
