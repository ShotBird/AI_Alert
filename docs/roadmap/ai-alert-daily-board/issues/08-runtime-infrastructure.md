## Question

매일 한 번 수집·요약을 돌리고 결과 JSON을 폰이 읽을 수 있는 곳에 올리는 구조를 확정한다.

후보:

- **GitHub Actions + GitHub Pages**: 공개 레포면 완전 무료. 다만 예약 실행이 **수 분~수 시간 지연**되고,
  공개 레포는 60일간 활동이 없으면 예약이 자동 비활성화된다
- **Cloudflare Workers + Cron Triggers**: 무료 티어로 충분하고 정시 실행이 훨씬 정확하다.
  대신 실행 시간 제한이 있어 무거운 처리가 어려울 수 있다
- **혼합**: Cloudflare가 정시에 깨워서 GitHub Actions를 `workflow_dispatch`로 호출 (조사 권고안)

함께 정할 것:

- **레포를 공개로 할 것인가** — 무료 CI와 Pages를 쓰려면 공개가 유리하지만,
  개인 관심사와 수집 소스 목록이 드러난다. API 키는 어차피 커밋하지 않지만 판단이 필요하다
- 사용자가 정한 시각을 어떻게 반영하는가 — cron을 매번 바꿀 수는 없으니,
  **자주 생성해두고 알림만 지정 시각에** 보낼 것인가?  이게 이 티켓의 핵심 설계 질문이다
- 오늘 것이 제시간에 안 나왔을 때 사람이 어떻게 아는가
- **무료 강제 장치를 어디에 둘 것인가** -- 일일 호출 카운터의 저장 위치(리포 커밋? 실행 환경 로컬?), fail-closed 처리, 개발 중 실수로 실제 API를 때리지 않게 하는 방법(fixture + --live 플래그), 매일 메일에 "네이버 12/300" 같은 사용량 한 줄 넣기

`grilling` + `domain-modeling` 스킬을 호출할 것.

## Answer

> **에이전트가 대신 결정함** (2026-09-20 야간 자율 세션).

### 결정

| 층 | 선택 |
|---|---|
| 리포 | **비공개** |
| 수집·요약 실행 | **GitHub Actions** (새벽 3시, 하루 1회) |
| 결과 배포 | **Cloudflare Pages** (보드 JSON + PWA 정적 파일) |
| 호출 카운터 | **리포에 커밋되는 JSON 파일** |
| 사용자 지정 시각 | **폰에서 해결.** 서버는 하루 한 번만 돈다 |

### 왜 공개 리포가 아닌가 — 이게 이 티켓의 핵심 판단

조사에서 확인된 사실: **GitHub Free는 공개 리포에서만 Pages를 제공한다.**
공식 문서 문구 그대로 — *"GitHub Pages is available in public repositories with GitHub Free … and in public and private repositories with GitHub Pro, …"*
(https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages)

즉 "무료 + GitHub Pages"는 **리포 전체 공개**를 요구한다. 그래서 갈림길은 셋이었다.

| 안 | 비용 | 공개되는 것 | 서비스 수 |
|---|---|---|---|
| A. 공개 리포 + Pages | 0원 | **전부** | 1 |
| B. 비공개 리포 + GitHub Pro | 유료(월 $4 선) | 없음 | 1 |
| C. **비공개 리포 + Cloudflare Pages** | **0원** | **없음** | 2 |

**C를 택한 이유는 프라이버시가 아니라 사고 반경이다.**

이 프로젝트에는 (1) 결제수단이 등록된 종량제 API 키가 있고, (2) 사용자가 비개발자다.
공개 리포에서 키를 한 번 잘못 커밋하면 그 즉시 남의 손에 들어가고, 그 키는 카드에 연결돼 있다.
`.gitignore`가 `.env`를 막고 있지만, 그건 **실수를 줄일 뿐 없애지는 못한다** — 스크린샷, 로그 출력,
설정 파일에 잠깐 적어둔 값처럼 우회 경로가 많다.

비공개 리포에서는 같은 실수의 결과가 "고치면 되는 일"이고, 공개 리포에서는 "키를 폐기하고 재발급하는 일"이다.
**비용이 같다면(둘 다 0원) 사고가 났을 때 덜 아픈 쪽을 고른다.** 보드 내용 자체는 공개돼도 무방하지만,
그 판단과 키 유출 위험은 별개다.

대가는 **서비스가 하나 늘어난다는 것**이다. Cloudflare 계정과 API 토큰을 GitHub 시크릿에 한 번 넣어야 한다.
비개발자에게 부담이지만, 일회성이고 그 뒤로는 건드릴 일이 없다.

### 무료 한도 확인

| | 한도 | 우리 사용량 |
|---|---|---|
| GitHub Actions (비공개) | 월 2,000분 | **약 90분** (하루 3분 × 30일) |
| Cloudflare Workers | 일 100,000 요청 | 하루 수십 |
| Cloudflare Pages | 월 500 빌드 | 월 30 |
| Cloudflare Cron Triggers | 5개 | 1개 |

전부 한 자릿수 % 사용률이라 여유가 크다.

### 사용자 지정 시각 — 서버 문제가 아니었다

이 티켓의 원래 질문은 "사용자가 정한 시각을 cron에 어떻게 반영하나"였는데, **질문 자체가 틀렸다.**
[04](04-notification-channel.md)에서 알림이 아이폰 단축어로 옮겨간 순간, 구조가 이렇게 갈린다.

- **서버**: 새벽 3시에 한 번 돌아 보드를 만들어 둔다. 사용자 시각과 무관하다
- **폰**: 사용자가 정한 시각에 단축어가 깨어나 그 보드를 가져와 알림을 띄운다

즉 **시각은 폰이 알고 서버는 모른다.** cron을 바꿀 일이 없다.
GitHub Actions의 예약 실행이 수 시간 늦을 수 있다는 문제도 이 구조에서는 무해하다 —
새벽 3시에 걸어두면 아무리 늦어도 아침까지는 끝나 있다. **Cloudflare cron으로 정시에 깨울 필요조차 없다.**

### 호출 카운터는 리포에 커밋되는 파일

세 후보를 비교했고 이유는 **fail-closed** 하나로 갈렸다.

- ❌ **Actions 캐시**: 7일 미사용 시 자동 삭제. 캐시 미스가 "카운터 0"과 구별되지 않아 **열린 채로 실패**한다. 탈락
- ❌ **리포 시크릿**: API로 다시 읽을 수 없다. 카운터로 못 쓴다
- ✅ **리포에 커밋되는 JSON**: 체크아웃이 실패하면 잡 자체가 죽으므로, 못 읽으면 호출도 못 한다. **자연히 닫힌 채로 실패한다**

부수 확인: `GITHUB_TOKEN`으로 푸시한 커밋은 워크플로를 다시 트리거하지 않는다(공식 문서 확인).
**무한 루프 걱정이 없다.** 하루 10KB씩 1년이면 3.65MB라 리포 크기도 문제되지 않는다.
